## Findings requiring disposition

### F1 — Dedicated customer receipt print workflow is absent (functional gap; medium)

**Reproduction:** log in as the QA owner, open Sales, then open a posted/partially returned QA sale. The sale-detail dialog contains the items, costs, payment history, return actions, and Close, but **zero Print/Receipt buttons**.

Native browser print-media emulation does leave the dialog visible and hides the application shell. However, the captured print-media screen still includes the dimmed sales-list background, dialog controls, and internal original-cost information. This is not proof of a clean customer receipt or successful printer output. No physical printer or OS print dialog was exercised.

**Evidence:** `artifacts/cloud/receipt-print.png`; the `Dedicated receipt print action` checkpoint is failed, while the narrower dialog-visibility/native-print-media checkpoint passed. No missing app print action was substituted with an invented passing click.

**Suggested next work:** explicitly decide the receipt requirement; if required, implement a customer-safe receipt view and print action, then rerun the hosted receipt contract and inspect print/PDF output. This QA commit does not implement it.

### F2 — Observed HTTPS auth cookie lacks `Secure` (hardening gap; low with HSTS mitigation)

After a real successful login and authenticated SSR reload, the observed auth cookie attributes were:

| Attribute | Observed |
| --------- | -------- |
| Secure    | `false`  |
| HttpOnly  | `false`  |
| SameSite  | `Lax`    |
| Path      | `/`      |

No cookie names or values are included here. The HTTPS response did advertise `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, which mitigates insecure transport in HSTS-aware clients; it does not make the missing cookie attribute true. JavaScript access/`HttpOnly=false` is expected for the current browser Supabase session flow and is **not** separately counted as a defect.

**Evidence:** `final-evidence.json`, checkpoint `HTTPS auth cookie Secure attribute`. Login failure handling, successful login, cookie existence, and SSR persistence passed independently.

**Suggested next work:** review production cookie options consistently across browser, server, and refresh handling; retain a working local-development policy. Retest real login, refresh, SSR, and logout after any change. No auth configuration was changed during QA.

## Reuse the opt-in cloud suite

Files: `playwright.cloud.config.ts`, `tests/cloud/cloud.spec.ts`, `tests/cloud/runner.ts`; `tests/cloud/summarize.ts` consolidates sanitized phase evidence without credentials or network calls.

The cloud config launches Playwright Chromium with the existing `@sparticuz/chromium` package. It does not start any webServer or import the fixture config. It requires the exact approved hosted origin/project, `.test` QA identities, a restricted credential-file mode, and an explicitly labeled matching QA shop before business operations.

```bash
# Safe default: skipped; no credential-file import and no cloud requests.
npm run test:cloud

# Explicitly approved real cloud run, using file paths rather than secret CLI values.
CLOUD_QA=1 CLOUD_QA_PHASE=bootstrap npm run test:cloud
# Operator executes the generated, narrowly scoped staff provisioning params
# through the approved Supabase execute_sql integration; do not print credentials.
CLOUD_QA=1 CLOUD_QA_PHASE=verify npm run test:cloud

# Read/rejection/UI recheck against the saved QA state; no new business events.
CLOUD_QA=1 CLOUD_QA_PHASE=confirm npm run test:cloud

# Login/cookie-attribute + retained table/report confirmation only.
CLOUD_QA=1 CLOUD_QA_PHASE=final npm run test:cloud

# Recompute the checkpoint summary without any network access.
node --import tsx tests/cloud/summarize.ts
```

The optional `supplemental` phase adds another UI product/sale/reversal and fractional-return scenario; normal `verify` now includes these as well. It is **not read-only**. Full verify appends fresh labeled QA data every time; it never resets or deletes old records. Already revoked staff is deliberately not reactivated: a fresh authorized QA account set is required to repeat the full active-to-revoked lifecycle. `CLOUD_QA_ACCOUNTS` and `CLOUD_QA_ENV` may point to operator-managed secure files with the existing shapes. Do not enable Playwright debug/trace/video capture, paste passwords into CLI arguments, or replace the approved project with an unrelated environment.

The mutation-origin preflight sends an invalid category payload using the real hosted Origin and requires validation status 400 before any business write. If it instead indicates a host Origin/configuration problem, the runner stops and the operator must escalate; it does not alter host configuration or try an alternate Origin.

## Limits

This is a real hosted QA run, not a proof against all schedules, all devices, all accessibility needs, or all accounting edge cases. The concurrency cases used one controlled attempt each (8-way retry, 2-way last unit, and return/checkout race), not a sustained load or outage test. Mobile means Chromium viewport emulation, not physical iOS/Android devices. Axe/focus checks do not replace screen-reader/manual accessibility testing. Unicode storage/search/CSV round trips were proved; bundled Chromium's CJK font fallback is not a guarantee of glyph coverage on every client. Multi-timezone reporting, unknown-cost products, sustained provider outages, long-lived token-expiry rotation, and real printer hardware were not comprehensively exercised here. CSV exports were downloaded and validated, not imported into a clean database. Blocked email delivery and independent restore must remain explicit release gates.
