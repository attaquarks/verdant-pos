# Product photo backend

Apply photo migrations 0004, 0005 and 0006 in order before enabling photo UI. Existing product queries and product columns are unchanged; an older database still serves the pre-existing inventory/product features. Photo endpoints return 503 if photo schema is not installed. No deployment or hosted testing was performed.

## UI contract

Use the existing authenticated cookie/session, not a service-role key. Image requests are same-origin and use normal browser credentials. There are no client-owned image-service accounts, upload credentials, or public image URLs.

**Two-phase product creation:**

1. Save the product using the existing `POST /api/actions/product`, with the original `request_id` and product payload. Wait for `{ok:true,data:{id:productId}}` before uploading. A timeout/ambiguous response must be retried with the **same product request ID and identical product payload**; do not create a second product. Keep the returned ID in UI state.
2. If a photo was selected, generate a **different** random UUID (`crypto.randomUUID()`) as the photo request ID. Send the file to the endpoint below. Product save and photo upload are separate transactions. If photo upload fails, show “Product saved; photo not saved” with retry/skip options, not overall product failure or a suggestion to create another product. Retain the product ID, photo request UUID, expected version and original selected file until a response is confirmed. If a reload loses the file, reopen the saved product, select it again and start a new photo request after fetching current version. No rollback of product data occurs.

**Upload or replace** `PUT /api/products/{productId}/photo` with raw file bytes, not multipart or JSON:

- `Content-Type: image/jpeg` or `image/png` or `image/webp` matching the actual file.
- `Origin` must match configured `APP_URL` (the browser supplies Origin for same-origin PUT).
- `X-Photo-Request-Id: <fresh UUID>`: one UUID per photo operation, different from the product-save UUID and every other operation. Keep it stable for retries. Its value becomes the image version.
- `X-Photo-Expected-Version: none` for a currently imageless product, otherwise the **last observed version UUID**. This header is required.
- Maximum raw request body 2,097,152 bytes; static images only, at most 16 million decoded pixels and 8,192 pixels per dimension. The decoder applies EXIF orientation, resizes to at most 1,600×1,600, strips metadata and converts to WebP. It bounds output to 2 MiB. Requests that are malformed, animated, spoofed, too large or fail decoding do not link an image. There are bounded processing and request-body timeouts. The website accepts a JPEG/PNG/WebP source of up to 12 MiB and 24 megapixels, resizes it in the browser before sending a bounded image, and the server independently verifies and re-encodes it. SVG and URLs are not accepted. The server only processes one frame; the browser may flatten supported animated source formats to a still image.

Success `200`: `{"ok":true,"product_id":"<uuid>","version":"<photo request uuid>"}`. Other statuses include `400` invalid data, `401` unsigned-in, `403` origin/access revoked, `404` missing or foreign product, `408` body/processing timeout, `409` stale expected version or reused key with different content, `413` size, `415` unsupported/mismatched type, `429` photo storage limit, `503` temporary/setup problem. Errors have `{"ok":false,"error":"..."}`. A 503/timeout might follow a committed write: retry the **identical file bytes, same request UUID and same expected version**; do not generate a new UUID until the outcome is resolved. A previously committed identical retry returns the original result, even if a subsequent photo replaced it. Always refresh the version list before displaying a success as the _current_ photo. If 409 indicates a conflicting edit, refresh the current version, ask the user before replacing it, and use a fresh UUID with that newly observed expected version. Do not blindly overwrite. Raw filenames are not sent or stored.

**Version lookup:** `GET /api/products/photo-versions?ids=<uuid>,<uuid>` (1–100 product IDs). Response `{"photos":[{"product_id":"<uuid>","version":"<uuid>"}]}`. Products without photos and inaccessible products are omitted. This separate optional lookup avoids altering existing DB read paths. Network/setup errors are not “no photo”; degrade gracefully with placeholders and an explicit photo error. `Cache-Control: private, no-store`.

**Display:** `GET /api/products/{productId}/photo` returns a decoded, sanitized `image/webp` with `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and a restrictive CSP. `404` means inaccessible/missing/corrupt photo, `401` unsigned-in, `403` revoked, `503` unavailable. No redirects, arbitrary URLs or remote fetches. An image URL may include `?v=<version>` as a UI cache-buster, but authorization and current metadata are checked on every request and the query value is ignored server-side. Use `<img src="/api/products/${productId}/photo?v=${version}">`; do not render an image if the version lookup omitted it. The parent UI owns layout: bound thumbnail dimensions without increasing the inventory row height, and show the full image within the product card. Do not show raw object paths.

## Security & implementation boundaries

- A private bucket accepts only JPEG/PNG/WebP MIME claims and at most 2 MiB per object. Storage object names are exactly `shop UUID/product UUID/photo request UUID` with no extension, filename, email, timestamp or user-entered text. Tenant- and product-aware RLS verifies active membership, canonical UUID path, product existence and an active reservation belonging to the uploader. Restrictive policies deny anon/cross-shop and prevent user UPDATE/DELETE or bucket moves even if an unrelated permissive policy is broad; unrelated bucket behavior is not changed. Existing restrictive policies and nonstandard privileged roles should still be audited before deployment. Migration fails rather than repurpose an existing bucket with incompatible settings.
- Metadata is in `product_photos`, separately keyed by `(shop_id, product_id)` with a version UUID. RLS permits only active-member reads. No direct authenticated writes are granted. `link_product_photo` verifies membership with the existing revocation lock, object path, object existence and uploader ownership, then transactionally applies expected-version comparison and the existing request-id/audit pattern. A product-row lock serializes first-upload and replacement races but does not modify product `updated_at`. Object upload and DB link cannot be atomic together.
- **A MIME claim is not proof of bytes.** A signed-in member can bypass the app API, call Supabase Storage directly with their own JWT, upload arbitrary bytes labelled as an allowed MIME type, and invoke the authenticated link RPC. PostgreSQL verifies identity, ownership and path, not image content. Therefore every application image GET independently decodes, pixel-limits and re-encodes stored bytes, rejecting malformed/animated data and never returning originals. Direct Storage access is a separate surface and does not have the app's decoding guarantees. Do not use Storage URLs as browser image sources. Full decoder isolation, WAF/rate limiting and antivirus scanning are not implemented; resource-heavy/hostile images remain a denial-of-service risk.
- Normal app reads reauthorize on every request and send `no-store`. Revocation blocks subsequent RLS reads and app requests, but cannot recall bytes a member has already downloaded or prevent copies/screenshots. Storage RLS is additionally restricted to the provider's authenticated-download and normal-upload operations. It denies signed-download and signed-upload URL issuance for this bucket, even if another permissive policy is later added. This is verified against the isolated operation-aware fixture; actual hosted Storage behavior must be independently exercised before release. An authorized person can still save a copy, and previously downloaded or cached bytes cannot be recalled after access is revoked.
- No application log includes photo bytes, original names, object keys or provider error details. Storage/provider/platform access logs may contain object paths or request IDs; they consist only of opaque UUIDs. Review provider log retention/access separately. EXIF location and metadata are stripped on both upload and app read; bypass-uploaded originals can still contain metadata accessible directly to authorized Storage users.

## Operations, retention and backups

There is no automatic image-object deletion. Failed requests, stale replacements and previous versions remain private and consume quota. Server-side reservations and Storage RLS enforce at most 150 existing photo objects plus unexpired pending reservations per shop and 400 across this bucket; objects are capped at 2 MiB each. Unuploaded reservations expire after 30 minutes; a retry must again fit quota if its earlier reservation expired. Reservations serialize quota checks and cannot be reused for another actor or product. This bounds photo-object storage, not total organization storage, bandwidth or processing cost; privileged operators and provider changes are outside this boundary. Old photo versions also count toward the cap, and there is not yet a safe self-service cleanup system. Plan and test lifecycle management before scaling. A future privileged reconciliation job should list only this bucket, compare object `(shop,product,version)` against current metadata **and idempotency/in-flight uploads**, retain candidates for a conservative grace period covering retries and in-flight requests, re-check immediately before deletion, and only then remove confirmed unreferenced objects. It must not delete on an ambiguous status or solely on age; no such job or grace period is implemented here. Coordinate cleanup with retries and expected-version conflict handling.

Postgres backups do not automatically back up Storage object bytes. Arrange separate private bucket backups, retention and restore drills consistent with database snapshots and orphan reconciliation. Protect backup access and signed URLs; restore metadata and matching bytes together. The additive migrations and private bucket were applied to the selected Verdant staging project. The currently deployed prototype points to that same project; existing shop transactions were not altered. The new photo UI is not yet promoted to the live deployment.
